# 在线接入方案

## 推荐结构

```text
GameEngine (唯一规则权威)
  -> 构造玩家公开观测
  -> 生成完整合法动作列表
  -> localhost HTTP /v1/decide
  -> 再次验证返回动作属于原列表
  -> GameEngine 执行动作
```

推理服务只加载模型，不加载游戏引擎和全部卡牌资源。当前哈希线性模型没有 NumPy、
PyTorch 等依赖，内存和 CPU 占用都很小；现有神经模型可以由单独的 Python 3.12 +
PyTorch 进程加载，未来也可导出 ONNX。游戏服务进程无需安装训练依赖，更不负责训练。

## 容错

建议每个 AI 决策：

1. 本机连接超时 20-50ms，总推理预算按模型实测设置在 100-200ms 内
2. 返回动作不在服务端刚生成的合法集合中时拒绝
3. 规则指纹不一致时拒绝
4. 超时、异常或拒绝后使用内置启发式策略
5. 连续失败时熔断 AI sidecar，稍后健康检查恢复

任何情况下都不应让推理服务直接修改房间或玩家对象。

`gtn_ai.client.InferenceClient` 已实现上述超时、协议解析、合法动作复验与策略回退，可由
未来的生产引擎适配层直接复用。

## API

`POST /v1/decide`：

```json
{
  "api_version": 1,
  "observation": {"schema_version": 3},
  "legal_actions": [
    {"schema_version": 3, "kind": "end_turn", "payload": {}}
  ]
}
```

响应：

```json
{
  "api_version": 1,
  "model": "hashed-linear-v1",
  "action_schema_version": 3,
  "action": {"schema_version": 3, "kind": "end_turn", "payload": {}}
}
```

`GET /health` 会返回协议版本、模型名与模型规则指纹。

## 性能容量

正式对局中 AI 只在轮到它决策时请求一次。即便在线人数增长，单个轻量模型也远小于
房间引擎和 Socket.IO 的常驻成本。上线前仍应做以下压测：

- 1、10、50、100 个并发决策
- P99 延迟和内存高水位
- 模型进程重启时的启发式回退
- 游戏更新后规则指纹拒绝旧模型

如果神经模型超过服务器预算，可采用三档方案：

1. 小模型在线推理，推荐
2. 大模型离线蒸馏成小模型
3. 对常见观测/动作特征缓存编码结果，但不缓存最终动作跨状态复用

## 上线步骤

1. 固定一版生产规则并记录规则指纹
2. 生成训练集，训练并通过离线擂台
3. 在测试服只记录建议动作，不真正执行，比较合法率和延迟
4. 仅开放给机器人/训练模式，保留启发式回退
5. 小流量正式启用并监控胜率、超时与崩溃
6. 规则更新后先训练新模型，再切换；不要关闭指纹检查

## 隐藏的 1v1 测试入口

游戏主页已经预留一个多人游戏 `1v1` 页内入口，但它当前不创建房间、不修改匹配，也
不是新的正式模式。入口采用三层门槛：

1. 浏览器已开启“特别致谢”隐藏功能
2. `/api/hidden-features/unlock` 已在服务端签名会话中记录解锁
3. 服务端显式设置 `GTN_AI_1V1_TEST_ENABLED=1`

三项同时满足且当前选中 `1v1` 时才显示。关闭特别致谢后会立即隐藏；仅伪造本地存储
不能通过服务端状态检查。现在点击只会说明尚未接入，因此可以先随代码保留而不会影响
玩家。模型通过擂台和延迟门槛后，再把它接到独立的“与 AI 对战”建房流程，仍复用正式
1v1 引擎与 UI，但不进入真人匹配队列，也不计花阶分。
